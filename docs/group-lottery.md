# 群抽奖规则及恢复约定

## 参与和开奖

所有类型都不要求认证，开奖时通过**所属机器人**逐人核验当前群成员，排除离群、被封禁和机器人自身。管理员不额外排除；仍在群内的禁言成员可以参与。资格API超时、权限不足、未知错误会暂缓整期，不把未知身份当成有效成员，也不偷偷改用其他奖池。机器人应为群管理员，保证成员查询可靠。

四种抽奖共用一套奖品配置：可添加多行「奖品名称 + 中奖人数」，总人数自动汇总，必须1—100。同一人每期只中一份。奖品按配置从上到下分配；发言排行按稳定排名从高到低对应奖品行，其他类型按抽出顺序对应奖品行。合格人数不足时按此顺序分配，未满额奖品空缺，不会改抽补位。开奖后把用户与奖品名称的对应关系持久化，公告重发使用同一快照，不会重新抽人或重分奖品。

- 发言加权：活动时间窗内至少达到设定发言数，按条数权重不放回抽满总人数；发言越多机会越高，但不保证中奖。
- 发言排行：本期发言数前N人；同分按Telegram数字ID升序，再按奖品配置顺序分配。
- 普通随机：本期发过言的不同用户均匀随机抽N人，不按发言数加权。
- 积分抽奖：设定1—1000000积分报名费用，用户点明确标价按钮后扣分，每人每期一次。从有效付费报名者中均匀抽N人，**不要求发言**，正常开奖未中奖不退款。

N必须1—100。开始和开奖时间必填，按北京时间存储；带时区API输入会转换北京时间。文字、图片、视频等共用计数路径，相册算一次；不补录机器人未收到/被过滤的消息。开始边界包含，报名截止边界不包含（`now < end`）；发言计数两端包含，在截止瞬间与原子开奖竞争，取得开奖锁后统一冻结。

**升级兼容**：旧certified/all_members配置键不再决定候选范围，不登录userbot或拉全群名单。历史随机活动在旧版没有累计发言，因此只能计入升级后实际收到的发言，无法补回升级前没有保存的记录。旧活动缺开始/开奖时间会显示错误，需后台补齐，不猜时间。仅有单一奖品描述和人数的旧活动会映射为一项奖品；其中旧的发言加权活动仍只抽1人。已结束且没有用户-奖品快照的旧结果不会被重新分配或重抽。

群里发「抽奖」、`/lottery`、`/lottery_list`可查看本群本机器人的当前活动，积分类型带报名按钮。列表和活动公告不展示活动编号。没有给普通随机新增点击报名制。

活动公告、群内列表和开奖结果使用同一套带适度表情的分段HTML排版，突出标题、奖品（前三档金银铜牌）和名单，不展示活动编号。开奖按奖品分组列出中奖者：可点击昵称链接、可选 @用户名，并同时用括号写出用户ID，例如 `<a href="tg://user?id=101">小明</a> @xiaoming（101）`。无昵称时链接文字用 @用户名或「一位成员」，ID仍要写出，不编造名字。开奖时把昵称/用户名写入中奖快照，补发和历史使用同一份名字，不因日后改名或重抽而变化。没有姓名快照的旧结果，展示时可读当前本地资料补全显示，但不回写、不重新分配奖品。不会为补名字向 Telegram 批量实查。

积分抽奖首次扣分成功后，除个人弹窗确认外，还会在点击按钮的群或频道发送一条公开短通知：用昵称（或 @用户名 /「一位成员」）作为可点击链接，不出现数字ID。失败、重复点击或已退款只弹个人提示，不再发群通知。

## 时间和状态

保存未来活动保持待开始；手动提前发预告也不会把未来活动改成进行中。开始状态约每60秒更新。**保存或到开始时间都不自动发布公告**，仍须点“发布公告”。

开奖约每60秒检查，不是精确到秒。手动开奖要求对应群管理员、所属机器人和正确活动ID，不允许未开始开奖。发言窗口内已开始的pending活动也能查询/计数，以免受状态更新tick影响。

原子领取开奖权后状态为drawing，计数/积分报名冻结，候选快照持久化。未能完成资格核验时保留可恢复状态，任务租约到期后继续；旧工作者被token隔离。群停用/插件关闭暂停自动开奖，恢复后补处理到期活动；机器人未运行时不领取开奖权。

结果、截止状态和每个群/频道目标的公告记录在同一事务提交。无人合格也结束并公告；已结束不能原地重开，请新建活动。已结束旧记录不会被批量补发公告。

## 积分安全和退款

报名唯一键为(活动ID,用户ID)，同一事务在父活动写锁下再次检查归属、窗口、开关、费用快照和余额，余额条件扣减、报名记录、积分流水一起提交。并发重复点击不重复收费，跨活动竞争也不能透支。旧按钮费用和当前设置不一致时拒绝扣分，要求刷新。

已有报名后活动参数锁定。删除未开奖的付费活动改为**逻辑取消**，同事务原额退款并保留报名/流水，重复取消不会重复退款；不能删除已结束付费活动。开奖时确认离群/封禁者原额退还，仍在群内但未中奖者不退。临时API错误不当作离群，不结算、不退款也不重抽，保留恢复或后台取消退款能力。

退款使用原始实扣金额，账户被旧逻辑删除时重建退款余额；参与过积分抽奖的账户在离群清理时保留，避免退款随后被清掉。退款、报名都写现有本群积分日志，无现金、支付、提现功能。

## 公告恢复和已知边界

每个目标独立持久化发送进度和已确认消息ID，成功目标不重发，失败分段约60秒后重试。已确认结果绝不因公告失败而重新抽人。HTML内容转义，消息按安全长度分段。

Telegram没有幂等键。如果消息已经送达但响应丢失，或收到响应后进程在保存进度前退出，该未确认分段可能重复。这里不承诺exactly-once。成员身份也只能是在调用Telegram时的快照，不能和Telegram加入/离开事件实现跨系统原子事务。

备份的活动配置包含积分费用，但不复制报名记录、退款状态或待发公告；不能用配置导入代替经济流水和数据库灾备恢复。

已有发言记录的活动也不能改类型或起止时间，避免把旧时间窗的累计数用于新活动；应新建活动。尚无记录的活动可以修改，开奖原子竞争时会再次校验最新时间窗。

含积分抽奖报名/退款流水的群组不能被级联删除，可停用以保留资金记录；仍有待发送中奖公告的群组也暂不能删除。

## 后台公告发布与头像加载

- 手动「发布公告」立即返回任务状态，页面显示“发送中”并查询最终结果，不再同步等 Telegram 20 秒。
- 每期活动有一个持久化发布槽位（独立 `lottery_publication` 表，由现有 `db.create_all` 建表流程创建），跨标签页/进程/重启防重。发送内容和目标在首次提交时冻结。
- 已确认发送的分片逐条保存进度。Telegram 明确拒绝（权限、参数、限流）才允许手动重试未发送部分。已成功发布的活动不提供再次群发按钮。
- 网络错误、超时、取消或发送中进程退出一律为“送达状态不明”，禁止自动或点击重发，先人工核对群和频道；本次不提供绕过锁的操作。排队但未开始的任务可在过期后安全重试。刷新页面会继续显示数据库里的状态。
- 公告全部成功后保留原有已到开始时间的 pending→active 行为，不提前激活未来活动，不更改候选人、积分、开奖记录或既有开奖补发规则。
- 头像 HTML 首先显示默认图，页面最多四路渐进加载；接口立即返回缓存图或默认图，拉图在后台完成，总预算 3 秒，失败缓存 45 秒，成功缓存 5 分钟。最多缓存 256 条、16 个进行中拉取，同一机器人/头像合并请求，失败后不在同页无限刷新。
- 拉图前已结束数据库读取并释放请求 Session，不把 ORM 实例带入网络协程。自动释放 SELECT 的 Session 现在先缓冲结果再提交，避免 PostgreSQL cursor 已关闭；显式流式查询由调用方负责事务生命周期。
- 这些改动缓解后台等待，不保证消除 Telegram 上游波动。未进行真实群发布、报名、扣分或测试开奖。
